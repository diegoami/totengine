## Delivered scope

Both `totplay` and `totdesktop` operate actual generated Original-profile games
with a selected human civilization and existing builtin-1 opponents. The browser
uses a packaged Rust loopback host and Canvas/DOM; desktop uses an independent
SDL2 window with direct calls. They share the resource loader, atlas, controller,
filtered human view, validated commands and replay-based checkpoint storage.
[Launch/controls and explicit limits](playable-clients.md).

Implemented paths: setup/resource diagnostics; known-map inspection and pan/zoom;
stack/unit activation; adjacent ground movement, scoped attack/occupation with
confirmation; wait/skip; typed city founding; own-city inspection and production
picker; initial/later research; explicit EndTurn and bounded opponents with
pause/continue; save/load at normal input and required research/founding.
Native text editing includes UTF-8 caret/selection and clipboard shortcuts.

Human views retain last-seen terrain and foreign cities; hidden later city
growth/name/ownership and roads do not leak through explored tiles. Current
foreign units require actual sight. Foreign notices/private policies, world
fingerprints, order logs and checkpoints do not enter the browser frame.
Format-2 human checkpoints reconstruct knowledge, private policies, RNG,
decisions, receipt identity and partial opponent state at the exact engine and
resource version. Invalid loads preserve the active game. New slot creation
does not overwrite old saves. Read/poll/reconnect/focus do not advance opponents;
loading partial opponent work requires explicit Continue.

## Retained evidence and reproduction

`docs/evidence/client-atlas-v1.json` records the reference resource identities
and 141 sprite dimensions, nontransparent counts and RGBA fingerprints. It
contains no pixels. First-slice crop/mask coordinates are implemented in
`crates/totui/src/client/atlas.rs`; existing five original opacity measurements
remain exact. This is our renderer policy, not exhaustive native atlas/style
or adjacency parity.

`docs/evidence/client-input-route-v1.json` records 879 UI inputs from a genuine
generated Original game: seed 2, 32×24, two civilizations, human 1, difficulty 0.
An existing built-in policy originally authored those test inputs; gameplay
executes through UI commands, without world/RNG injection. The route fights a
ground battle and occupies/razes city 4 by round 67. This is automated fixture
evidence, never owner acceptance. Reproduction binds typing to the current
presentation field token; stale token rejection is covered separately.

```sh
export CIVTOT_HOME=/mnt/d/games/CIVTOT
TOTENGINE_ENCOUNTER_OUT=/tmp/client-encounters cargo test -p totui \
  generated_land_encounter -- --ignored --nocapture
cargo test -p engine --lib human::tests
cargo test -p totui --lib
```

The generated route emits private before/after battle/capture `.cth` fixtures
and actor/direction/result JSON. These are engine-generated checkpoints, not
original SAV files. `tools/check_client_browser.cjs`, `check_client_linux.py`
and `check_client_windows.ps1` exercise actual mouse/keyboard or OS keyboard
input against ordinary executables. They save pending research/founding,
choose Warriors production, reach turn 11, reload each choice, take the next
action, and test combat/capture cancellation/retry using those generated files.
The test-only native trace is enabled explicitly by environment and never
served over HTTP. Screenshots and traces with owned art stay outside Git.

Browser checker needs Playwright/Chromium installed separately:

```sh
TOTENGINE_SAVES=/tmp/client-browser totplay --no-open --port=8774
# In another terminal; NODE_PATH can identify an existing Playwright install.
TOTENGINE_CLIENT_ORIGIN=http://127.0.0.1:8774 \
TOTENGINE_CLIENT_SAVES=/tmp/client-browser \
TOTENGINE_ENCOUNTER_FIXTURES=/tmp/client-encounters \
node tools/check_client_browser.cjs
TOTENGINE_ENCOUNTER_FIXTURES=/tmp/client-encounters \
python3 tools/check_client_linux.py
```

Linux checker needs Xvfb/libX11/libXtst and the built native executable; it uses
an authenticated private display and cleans up its own processes. Windows
checker accepts `-Binary` and `-Work`; `CIVTOT_HOME` must be a Windows path,
and `TOTENGINE_ENCOUNTER_FIXTURES` a Windows-readable path. It guards the
foreground window by process identity before every key and refuses to type into
another app. Each route requires a new save folder. `TOTENGINE_CLIENT_BINARY`
selects a packaged Linux executable. Desktop builds need SDL2 development/link
files and `--features desktop`; see the proven platform setup in
[desktop feasibility](ui/desktop-feasibility.md).

Browser and Linux normal/pending-choice/ten-round files are byte-identical;
the retained Windows ten-round run matches the same four initial checkpoints.
Next-choice continuation and encounter comparison results are recorded in
`docs/evidence/playable-client-checks.json`. Windows runs that lost foreground
or encountered a test-driver punctuation mapping problem are not counted as a
completed extended package route. The punctuation driver now uses alphanumeric
slot names. Automated checks cannot establish usability or owner acceptance.

## Material limits and review gate

Full city management, switching penalties, government/diplomacy, sea/air/cargo,
map-edge wrapping moves, SAV import/export, scenarios/multiple maps, native
victory and sustained full campaigns remain outside this accepted slice.
The existing capture kernel has explicit capital/civil-war/technology/respawn
limits, shown before acceptance. Unsupported mandatory government stops with a
resumable checkpoint. Art uses a generic city style, authored owner markers and
simple road/river marks; complete native layout/palette/coast/style parity is
not claimed. Native selection is functional but lacks selection highlighting;
long names/paths do not provide a horizontally scrolling desktop text field.
These remain explicit first-slice limitations; the owner reported no blockers.
